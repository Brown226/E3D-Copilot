## 三、P0 — 用户体验刚需

### E1. 子代理前端可视化 ✅ 当前迭代

**现状**：`CopilotEvent.AgentName` 字段已就绪，但前端 `MessageList.tsx` 未消费该字段，子代理输出与主 Agent 混在一起。

**目标**：让用户在 UI 中清晰看到子代理的独立运行状态。

**改动清单**：

1. **`MessageList.tsx` 分组渲染**：按 `AgentName` 字段分组，子代理消息以独立卡片/折叠面板展示，顶部显示 `[子代理: name]` 标签
2. **`messageContracts.ts`**：新增 `SubagentMessage` 类型（含 `agentName`/`agentStatus`），区别于主对话消息
3. **`ToolCard.tsx`**：`dispatch_subagent` 工具调用显示特殊图标（多人头图标）+ 子代理名称
4. **`useChatStore.ts`**：新增 `subagentMessages` 字段，独立管理子代理消息列表
5. **实时状态**：子代理运行中时前端显示 "🤖 name 正在工作..." 的 loading 状态

**验证**：手动测试——派发 `dispatch_subagent(name="test", task="query")` 后前端显示独立面板

**工作量**：S~M（约 3 天）

### E2. 子代理写模式（安全受限）

**现状**：`SubagentDispatchHandler.IsReadOnly = true` 硬编码，子代理只能使用只读工具。但实际场景中，子代理往往需要执行写入操作（如"去检查管道 A 的属性，然后修改管道 B 的属性"）。

**目标**：允许子代理在受控条件下执行写操作。

**安全设计**：

| 风险 | 防护 |
|---|---|
| 子代理绕过审批 | 写操作**仍走主 Agent 审批流**——子代理 `ExecuteAsync` 结果作为 tool result 回到主 Agent，由主 Agent 执行实际写入 |
| 写操作不可审计 | 子代理的写工具调用携带 `AgentName` 标签，日志中可追溯 |
| 误操作 | 可配置 `SubagentConfig.AllowWrite` 白名单，默认关闭 |

**改动清单**：

1. **`SubagentContext.IsReadOnly`**：改为可配置（`dispatch_subagent` 参数 `readonly=false` 时允许写）
2. **`SubagentRunner.RunAsync`**：`IsReadOnly=false` 时不调用 `FilterReadOnly()`，使用完整工具集
3. **`SubagentDispatchHandler`**：`IsReadOnly` 改为动态——派发本身是只读，但子代理是否只读取决于参数
4. **审批流**：子代理内写工具调用 emit 的 `ApprovalRequest` 必须有 `AgentName` 标记，主 Agent 审批时可见

**防护**：子代理内仍禁用 `dispatch_subagent`（防递归），`MaxSubagentDepth=2` 不变。

**工作量**：M（约 5 天）

## 四、P1 — 协作与可靠性

### E3. Planner-Executor 编排引擎

**现状**：`SubagentMode.Planner` 和 `SubagentMode.Executor` 枚举值已存在，但没有真正的编排逻辑——`Planner` 模式不会自动产出计划供 `Executor` 执行。

**目标**：实现真正的 Planner→Executor 协作流程，对齐 Reasonix `coordinator.go` 的编排模式。

**设计方案**：

```
主 Agent 识别复杂任务
  │
  ▼
Planner 子代理（只读分析 → 输出结构化计划）
  │
  ▼
主 Agent 审查计划（可修改/确认）
  │
  ▼
Executor 子代理 1 ──→ 执行子任务 A
Executor 子代理 2 ──→ 执行子任务 B（并行）
Executor 子代理 3 ──→ 执行子任务 C
  │
  ▼
主 Agent 汇总结果 → 最终输出
```

**改动清单**：

1. **新建 `Agents/Orchestrator.cs`**：`PlannerExecutorOrchestrator` 类，管理编排流程：
   - `Plan(task)` → 派发 `Planner` 子代理，产出结构化计划（JSON 格式，含步骤列表、依赖关系、并行分组）
   - `Execute(plan)` → 按依赖关系分组派发 `Executor` 子代理，同一组并行执行
   - `Summarize(results)` → 汇总各子代理结果
2. **`SubagentDispatchHandler` 新增 orchestrate 模式**：参数 `mode="orchestrate"` 时，自动触发编排流程而非单次派发
3. **`SystemPrompt.cs`**：增补编排能力的说明，让主 Agent 知道什么时候用编排
4. **新工具 `orchestrate_task`**（可选）：比 `dispatch_subagent` 更高层的工具，主 Agent 只需要描述任务，由 Orchestrator 自动分解

**工作量**：L（约 10 天）

### E4. 工具调用自动重试 + 降级

**现状**：`ToolExecutor.ExecuteAsync` 执行失败时，直接将错误文本返回给 LLM，由 LLM 决定是否重试。缺少自动重试策略。

**目标**：对可重试的失败（网络超时、临时错误）自动重试，对不可重试错误给出降级建议。

**改动清单**：

1. **`IToolHandler` 新增 `MaxRetries`**：默认 0（不重试），可重写
2. **`ToolExecutor.ExecuteAsync` 重试逻辑**：对 `MaxRetries > 0` 的 handler，遇到 `ToolResult.IsRetryable` 时自动重试（指数退避，100ms/200ms/400ms）
3. **`ToolResult` 新增 `IsRetryable`**：区分网络错误（可重试）与业务错误（不重试）
4. **降级策略**：重试耗尽后，LLM 看到 `[retry exhausted after 3 attempts, last error: ...]`，可自主选择降级路径

**工作量**：M（约 3 天）

## 五、P2 — 体验打磨

### E5. 跨会话记忆共享

**现状**：`MemoryManager` 使用 SQLite 持久化存储，但当前仅限于单会话内检索。跨会话时记忆不会自动继承。

**目标**：让不同会话间共享知识——用户画像、常用操作、偏好元素类型。

**改动清单**：

1. **`MemoryManager.GetSystemPromptContext()`**：当前已返回「用户画像 + 项目知识」，需确保跨会话时 `CopilotController` 初始化时自动加载历史画像
2. **`CopilotController` 启动时加载**：`CreateDefault` 中 `MemoryManager` 构造后立即调用 `LoadProfile()` 恢复上次会话的用户画像
3. **`MemoryManager.Compact()`**：记忆条目过多时的压缩策略（合并相似记忆、清理过期条目）

**工作量**：M（约 5 天）

### E6. 对话分支 + 回退

**现状**：对话是线性结构——不支持回退到历史某一步重新尝试。

**目标**：允许用户回退到之前的某个 turn 重新开始，或者分支探索不同方案。

**改动清单**：

1. **`CopilotSession` 新增 `Checkpoint(int turnIndex)`**：保存当前 session 快照
2. **`Rollback(int turnIndex)`**：恢复 session 到指定 turn 的状态
3. **前端 UI**：每条消息右上角加「从这继续」按钮，点击后回退到该 turn 并清空后续消息
4. **`CopilotController` 新增 `SwitchBranch(int turnIndex)`**：处理分支切换逻辑

**注意**：分支后已执行的写操作无法"撤销"（E3D 数据已修改），需在 UI 提示用户。

**工作量**：M（约 5 天）

## 六、P3 — 架构升级

### E7. 多 Agent 架构统一（Coordinator 模式）

**现状**：当前子代理是"主 Agent 手动派发"模式——主 Agent 决定何时派发子代理。缺少一个统一的 Agent 团队管理层。

**多 Agent 系统调研结论**：

| 方案 | 框架要求 | 兼容性 | 结论 |
|---|---|---|---|
| Microsoft Agent Framework | .NET 8+ | ❌ 不兼容 | 跳过 |
| AutoGen .NET (v0.4+) | .NET 8+ | ❌ 不兼容 | 跳过 |
| Semantic Kernel 1.0+ | .NET 6+ | ❌ 不兼容 | 跳过 |
| 手写 Coordinator（借鉴 Reasonix）| 无额外依赖 | ✅ 完全兼容 | **推荐采用** |
| LangGraph（Python）| Python 进程外 | ⚠️ 间接 | 不推荐（增加运维复杂度）|

**推荐方案：手写 Coordinator 模式**（借鉴 Reasonix `internal/agent/coordinator.go` + `subagent_store.go`）

**Coordinator 核心职责**：

```
┌─────────────────────────────────────┐
│          Coordinator                │
│  ┌───────────┐  ┌───────────────┐   │
│  │ Agent     │  │ Subagent      │   │
│  │ Registry  │  │ Store         │   │
│  │ (name→    │  │ (context→     │   │
│  │  factory) │  │  result)      │   │
│  └───────────┘  └───────────────┘   │
│  ┌───────────┐  ┌───────────────┐   │
│  │ Schedule  │  │ Handoff       │   │
│  │ (并行/串行)│  │ (专长切换)    │   │
│  └───────────┘  └───────────────┘   │
└─────────────────────────────────────┘
```

**改动清单**：

1. **新建 `Agents/Coordinator.cs`**：
   - `AgentRegistry`：注册具名 Agent 工厂（如 `"inspector"` → `SubagentRunner` + 专有提示词）
   - `SubagentStore`：缓存子代理结果，避免重复派发
   - `Schedule(DAG)`：按依赖图调度执行，并行组 `Task.WhenAll`
   - `Handoff(from, to, context)`：专长切换——当前 Agent 暂停，目标 Agent 从上下文恢复
2. **`AgentRegistry` 预置专长 Agent**（通过 `CopilotConfig` 配置）：
   - `inspector`：元素属性查询专长
   - `designer`：设计修改专长
   - `reporter`：报告生成专长
   - `piping-engineer`：管道专长
   - `structural-engineer`：土建结构专长
3. **`SystemPrompt.cs`**：告知主 Agent 有哪些专长 Agent 可用，何时使用 handoff
4. **`CopilotConfig` 新增 `SpecializedAgents`**：可配置的专长 Agent 列表（名称、提示词、默认模型）

**工作量**：XL（约 15 天，可分 3 个迭代完成）

### E8. 评估与幻觉检测

**现状**：LLM 输出直接展示给用户，没有验证机制。

**目标**：对关键输出（工具调用结果、数值计算）进行自动验证。

**改动清单**：

1. **`CopilotEvent` 新增 `Confidence` 字段**：LLM 输出的置信度标记（high/medium/low）
2. **`AgentLoop` 后处理**：提取工具结果中的数值，与 LLM 回答中的数值进行交叉验证
3. **`SystemPrompt.cs`**：要求 LLM 在引用工具结果时标注来源（如 `[from: query_pipe_info]`）
4. **前端标记**：低置信度输出显示 ⚠️ 标记

**工作量**：M（约 5 天，MVP 先做简单正则匹配）

## 七、多 Agent 系统深度分析

### 7.1 为什么不能直接上现成框架

| 框架 | 最低 .NET 版本 | 包体积 | 是否可嵌入 E3D | 结论 |
|---|---|---|---|---|
| Microsoft.Agents (v1.0+) | .NET 8 | >10MB | ❌ 进程外设计 | 不兼容 |
| AutoGen.NET (v0.4+) | .NET 8 | >5MB | ❌ 需要 ASP.NET Core | 不兼容 |
| Semantic Kernel (v1.18+) | .NET 6 | >3MB | ⚠️ 部分可用但 net48 不支持 | 不兼容 |
| 手写 Coordinator | 无要求 | 0 | ✅ 完全兼容 | **推荐** |

### 7.2 推荐架构：Reasonix 风格 Coordinator

Reasonix 的多 Agent 架构（`internal/agent/`）因其**零外部依赖、纯 Go 标准库、清晰的子代理生命周期管理**，与 E小智的约束高度匹配。核心概念映射：

| Reasonix 概念 | E小智映射 | 状态 |
|---|---|---|
| `AgentProcess` | `AgentLoop` | ✅ 已有 |
| `SubagentSpec` | `SubagentContext` | ✅ 已有 |
| `SubagentStore` | `SubagentRunner` 结果缓存 | ⏳ E7 实现 |
| `Coordinator` | `Orchestrator` | ⏳ E3 实现 |
| `Handoff` | `SubagentDispatchHandler + PreferredProvider` | ⏳ E7 实现 |
| `AgentRegistry` | `ProviderRegistry` 风格的 Agent 工厂 | ⏳ E7 实现 |

### 7.3 双模型选择策略（C2 增强）

当前 C2 已支持 `PreferredProvider` 字段，但缺少自动选择策略。建议：

1. **静态策略**（简单）：配置中为每个专长 Agent 指定固定模型
2. **动态策略**（高级）：Planner 用高推理模型（如 `deepseek-reasoner`），Executor 用高性价比模型（如 `Qwen3.5-32B`）
3. **回退策略**：目标模型不可用时，自动回退到主 Provider

### 7.4 专长 Agent 配置示例（CopilotConfig）

## 八、不建议跟进项

| 项 | 原因 |
|---|---|
| 多 Agent 框架引入（MAF/AutoGen/SK）| net48 不兼容，编译失败；升级 .NET 破坏 E3D 宿主 |
| 跨进程 Agent 通信（A2A）| 单进程单宿主，无跨进程需求 |
| 独立 Agent 运行时 | E3D 进程内加载，无需独立运行时 |
| 图数据库记忆 | SQLite 足够，图数据库过度设计 |
| 完整 MAF Workflow 引擎 | 手写编排足够，Workflow 引擎是过度工程 |
| Agent 热加载 | .NET Framework 4.8 无法卸载程序集，热加载不可行 |
